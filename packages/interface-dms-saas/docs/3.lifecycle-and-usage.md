# Lifecycle and usage

Use the direct subpaths below or the root's `invoiceLineItems` and `tenantLifecycle` namespaces. Register consumers/providers from the owning module's lifecycle, not a request handler. Registrations replay when SaaS attaches or reloads and are released when their owner unloads.

## Choose when your work should happen

| Task | Integration | Example result |
| --- | --- | --- |
| Save onboarding answers | Provisioning hook | A referral code is stored before signup completes |
| Create paid product resources | `created` lifecycle consumer | A workspace gets its resources after payment is committed |
| Pause or resume resources | Lifecycle consumer | SaaS access waits for the required reactivation receipts |
| Add measured usage to a bill | Invoice line-item provider | 120 compute minutes produce one priced line |

For that last example, `amountCents: 600` and `quantity: 120` mean a line total
of €6.00 on an EUR invoice, not 120 × €6.00. Your resolver calculates the total;
SaaS does not multiply it by the quantity. See the
[working provider example](/docs/modules/saas/extending#invoice-line-items)
before implementing the contract below.

## Invoice line items

Import from `/invoice-line-items`. `RegisterInvoiceLineItemsProvider(provider: InvoiceLineItemsProvider): void` registers `{ id: string, resolve: InvoiceLineItemsResolver, onUsageGap?: (gap: InvoiceUsageGap) => void }`. `UnregisterInvoiceLineItemsProvider(providerId: string): void` removes it; unknown IDs are ignored. Register during `construct()` and unregister during `stop()`.

```ts [Contract]
interface InvoiceLineItemsContext {
  tenantId: string;
  invoiceId: string;
  currency: string;
  periodStart: Date;
  periodEnd: Date;
  isPreview?: boolean;
}

interface InvoiceLineItem {
  key: string;
  description: string;
  amountCents: number;
  quantity?: number;
  unit?: string;
  metadata?: Record<string, string>;
}

type InvoiceLineItemsResolution =
  | { status: "ready"; lines: InvoiceLineItem[] }
  | { status: "not_ready"; reason: string };

interface InvoiceUsageGap {
  tenantId: string;
  invoiceId: string;
  periodStart: Date;
  periodEnd: Date;
  reasons: string[];
}

type InvoiceLineItemsResolver = (
  context: InvoiceLineItemsContext,
) =>
  | Promise<InvoiceLineItem[] | InvoiceLineItemsResolution>
  | InvoiceLineItem[]
  | InvoiceLineItemsResolution;
```

The runtime asks providers for `subscription_cycle` renewal invoices, not initial or one-off invoices. The dates cover the cycle just closed, clipped to the subscription's paid usage period. Complimentary/grace usage is excluded; no provider runs for an empty covered window. Read tenant-scoped, pre-aggregated usage because the resolver runs inside the webhook request or the recovery worker, and return the same lines every time for a closed window.

`amountCents` is the safe-integer line total in the invoice currency, including negative credits. Quantity and unit are audit metadata, not factors multiplied into the total. Zero amounts are dropped. Empty keys/descriptions, non-safe-integer amounts, keys containing `:`, or combined keys over 150 characters are invalid. Provider IDs must not contain `:`; registration throws if they do. IDs must be globally unique across modules: a collision replaces the earlier provider, and collisions before attachment can collapse silently.

Keep each line key stable. The runtime injects at most one line per invoice/provider/key across webhook replays and concurrent workers. Returning lines is not a guarantee that Stripe accepted the invoice items.

On a closing invoice the runtime first suspends the draft (`auto_advance=false`) and hands the injection to a durable task. The invoice is always finalized: once every provider's lines are on it, or 48 hours after it was registered with the lines available:

| Resolver answer | Effect |
| --- | --- |
| An array, or `{ status: "ready", lines }` | The lines are injected; an empty array states an empty bill. |
| `{ status: "not_ready", reason }`, or a thrown error | The draft stays suspended and the provider is asked again later; past the deadline, the invoice is finalized without its lines. |
| Anything else | Treated as `not_ready` with reason `invalid_resolution` (`INVALID_RESOLUTION_REASON`); `normalizeInvoiceLineItemsResolution` applies that rule. |

An invoice finalized without some of its lines — a provider not ready at the deadline, invalid lines, Stripe refusing a line, or a draft changed outside dms-saas — never bills the missing usage: the gap favours the customer. The runtime logs it at error level (`invoice finalized with missing usage`) and calls `onUsageGap` on every provider the invoice was registered with, so the provider can raise an alert and its owner can fix the system. Each reason starts with a stable code (`provider_not_ready`, `managed_lines_unexpected_or_changed`, `before_finalize`, ...) followed by `:` and its detail.

`periodStart` is inclusive and `periodEnd` exclusive, so two adjacent cycle invoices cover disjoint windows. A preview covers the open cycle up to the request time; it is a quote of the next invoice, not an addition to it. A negative `amountCents` is a credit line.

A provider that may still be loading when an invoice is created is listed in the runtime's `invoiceLineRequiredProviders` option so the invoice waits for it. See the [runtime configuration](/docs/modules/saas/configuration).

Preview calls set `isPreview: true`, use a synthetic `upcoming_<subscription id>` invoice ID, and end at the request time. They quote usage without invoicing it. Do not mutate usage accounting inside a resolver. A failed resolver or invalid line makes the preview unavailable.

### Line helpers

`LINE_KEY_SEPARATOR` is `":"`. `buildInvoiceLineKey(providerId: string, key: string): string` joins the two fragments; it does not validate them.

`selectInvoiceLineItemsToCreate(providerId: string, items: readonly InvoiceLineItem[], alreadyInjectedKeys: ReadonlySet<string>): InvoiceLineItemSelection` is synchronous and has no Stripe side effects. It returns `accepted: PreparedInvoiceLineItem[]` (`{ lineKey, item }`, with trimmed item keys) and `skipped: SkippedInvoiceLineItem[]` (`{ lineKey, reason }`). `SkippedLineItemReason` is `already_invoiced`, `duplicate_key`, `zero_amount`, or `invalid`. The set must contain full provider-prefixed keys. This selection helper does not itself provide transactional idempotency.

## Plan changes

Import from `/plan-changes`. A module that owns tenant inventory (applications, environments, seats it counts) registers the policy SaaS consults before a paid-to-Free downgrade lands:

```ts [Contract]
import type {
  PlanChangeIncompatibility,
  PlanChangeValidationRequest,
} from "@antelopejs/interface-dms-saas/plan-changes";

interface PlanChangePolicy {
  name: string;
  validatePlanChange(
    request: PlanChangeValidationRequest,
  ): Promise<PlanChangeIncompatibility[]>;
}
```

`RegisterPlanChangePolicy(policy)` registers the sole policy and `UnregisterPlanChangePolicy(name)` removes it; registering opts deferred changes into the guarded paid-to-Free flow. `validatePlanChange` runs for the `preview`, `schedule` and `effective` phases; the effective call runs after DMS tenant admission is paused and earlier membership writers have drained. It must not mutate inventory or call Stripe. A missing policy, when the runtime's `requiredPlanChangePolicy` names one, fails closed.

| Function | Use |
| --- | --- |
| `GetTenantPlanConstraints(tenantId)` | Current and pending plan, `blocked`/`admissionBlocked` and the incompatibilities, for inventory writers to check after entering their own admission. Read-only, not a reservation. |
| `CountOccupiedSeats(tenantId)` | Occupied seats, including unexpired invitations and excluding platform support. |
| `GetPlanChangeActivation(tenantId)` | `{ planChangeOperationId, operationId, gateId }` of the only downgrade hold an activation consumer may release, or `null`. Match both operation IDs on the lifecycle message, evaluate every DMS access gate (`EvaluateTenantAccess`) and preserve every other denial. |

`TenantLifecycleMessage.planChangeOperationId` marks a lifecycle delivery produced by a guarded downgrade; never treat one you cannot authorize as an ordinary resume.

## Tenant lifecycle

Import from `/tenant-lifecycle`. `TENANT_LIFECYCLE_TRANSITIONS` contains `created`, `suspended` and `reactivation_requested`; `TenantLifecycleTransition` is their union.

**Breaking migration:** Update `@antelopejs/interface-dms-saas` and `@antelopejs/dms-saas` together. The old `RegisterWorkspaceLifecycleConsumer`, `UnregisterWorkspaceLifecycleConsumer`, `WorkspaceLifecycle*` types, `WORKSPACE_LIFECYCLE_TRANSITIONS`, `IsWorkspaceProvisioningCommitted`, `/workspace-lifecycle` subpath and root `workspaceLifecycle` namespace are removed, without compatibility aliases. Use the tenant-named API below and root `tenantLifecycle` namespace instead. Persisted consumer IDs, transition values and operation IDs remain unchanged; keep existing consumer names and deduplication keys.

```ts [Contract]
import type { TenantLifecycleTransition } from "@antelopejs/interface-dms-saas/tenant-lifecycle";

interface TenantLifecycleMessage {
  tenantId: string;
  operationId: string;
  transition: TenantLifecycleTransition;
  requestedAt: Date;
}
interface TenantLifecycleReceipt {
  receiptId: string;
  effectiveAt?: Date;
}
interface TenantLifecycleConsumer {
  name: string;
  transitions: readonly TenantLifecycleTransition[];
  consume(message: TenantLifecycleMessage): Promise<TenantLifecycleReceipt>;
}
interface TenantLifecycleConsumerRegistration { unregister(): void; }

declare function RegisterTenantLifecycleConsumer(
  consumer: TenantLifecycleConsumer,
): TenantLifecycleConsumerRegistration;
declare function UnregisterTenantLifecycleConsumer(name: string): void;
declare function IsTenantProvisioningCommitted(tenantId: string): Promise<boolean>;
```

Names must match `/^[a-z][a-z0-9._-]{2,63}$/`; invalid names throw synchronously. Pick a stable unique name and explicitly select transitions. Unregister via the returned handle or by name when the module stops.

Delivery is **at least once**. Deduplicate by `operationId`, durably link provisioned resources, then return a durable receipt. A rejection is not an acknowledgement. Suspension closes SaaS access before delivery; reactivation keeps access closed until every registered required consumer returns a receipt. `created` arrives after ownership, billing and pre-provisioning hooks succeed and the first invoice is paid, or no payment is required.

`IsTenantProvisioningCommitted` returns false for preparing, unpaid or cancelled self-service workspaces; true for committed creations and legacy/bootstrap tenants without a marker. It is not an existence, membership or access check. Storage and missing-implementation errors propagate; fail closed instead of treating an unavailable check as eligibility.

## Registration and provisioning

`TenantBeingProvisionedPayload` from `/provisioning` has `tenantId: string`, optional `userId: string`, and optional `extras: JsonObject` (from `/json`, with `JsonValue`). Use it with the DMS `Hook.TENANT_BEING_PROVISIONED` hook; the hook handler returns `Promise<undefined>`, not `Promise<void>`. The runtime fires the hook through DMS `ProvisionTenant`, which registers the workspace's tenant-schema instance before any listener runs. DMS also fires it once for its `default` tenant, at its creation and without `userId`: write a tenant's default data in this hook, never in `start()` or `DATABASE_INITIALIZED`.

Listeners run serially inside provisioning, while the per-card lock is held, after workspace records exist but before registration returns. A throwing listener cancels registration and rolls back the runtime's tenant, subscription, Stripe customer and password-path account. Do not assume external side effects of your listener roll back automatically. Keep it to bounded persistence work rather than network provisioning; use durable `created` delivery for post-payment resources.

Extras reach password and OAuth completion paths unchanged, are absent when nothing was captured, and remain consumer-owned. The runtime does not persist or return them. `/registration` exports `RegistrationExtrasLimits` and `REGISTRATION_EXTRAS_LIMITS`: `maxSerialisedBytes: 4096`, `maxKeys: 64`, `maxDepth: 4`. Public registration also rejects `__proto__`, `constructor`, and `prototype` keys. Rejected extras produce HTTP 400 `saas.errors.registration.extras_*` errors before listeners run.
