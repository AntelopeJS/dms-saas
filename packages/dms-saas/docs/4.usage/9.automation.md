When the automation module is installed, the SaaS module adds the nodes below to its builder. Without it, the SaaS module registers nothing and runs as usual. Every node is named in the reader's language. No node moves money: no node changes a plan, issues a credit note or refunds; the credit note and refund triggers only observe Stripe.

## Triggers

Every trigger outputs `tenantId` (the workspace), `deliveryId` and `at` (ISO 8601), and fires on the instance that processed the change (`replicated`).

`deliveryId` is equal on every re-emission of the same event. Wire it into the `idempotencyKey` of an action with an external effect, so a replayed event does not act twice.

| Trigger | Fires when | Settings | Outputs besides the common ones | `deliveryId` |
| --- | --- | --- | --- | --- |
| `saas.subscription-started` | A Stripe Checkout completes, or a workspace created with a card has its first invoice paid | none | `source` (`checkout`, `provisioning`), `planId`, `status` (`active`, `trialing`), `stripeSubscriptionId`, `trialConsumptionRecorded` | Checkout: the Stripe event id. Provisioning: `subscription-started:<stripeSubscriptionId>` |
| `saas.subscription-cancelled` | Stripe ends a subscription, or an owner deletes a workspace (paid or free) | none | `source` (`stripe`, `workspace_deletion`), `stripeSubscriptionId` (null for a workspace deleted without one) | Stripe: the event id. Deletion: `workspace-deletion:<operation id>` |
| `saas.payment-failed` | An invoice payment fails and the workspace goes past due | none | `invoiceId`, `invoiceNumber`, `amountDue` (minor units), `currency` | Stripe event id; each retry attempt is a new event |
| `saas.trial-ending` | Stripe announces the end of a trial | none | `trialEndsAt` | Stripe event id |
| `saas.invoice-paid` | A workspace invoice is paid in Stripe | `includeZeroAmount` (off: invoices with nothing paid are skipped) | `invoiceId`, `invoiceNumber`, `amountPaid` (minor units), `currency`, `billingReason`, `hostedInvoiceUrl`, `reactivated` (the payment lifted a past due or suspended workspace) | Stripe event id |
| `saas.credit-note-issued` | A credit note is issued on a workspace invoice | none | `creditNoteId`, `number`, `invoiceId`, `invoiceNumber`, `amount` (minor units), `currency`, `type`, `reason`, `refundId`, `pdfUrl` | Stripe event id |
| `saas.refund-updated` | A refund on a workspace payment changes status | `status` | `refundId`, `status` (`pending`, `succeeded`, `failed`, `canceled`), `amount`, `currency`, `failureReason`, `creditNoteId`, `chargeId` | Stripe event id |
| `saas.billing-state-changed` | A workspace's billing state changes, for example trialing to active | `toState`, `fromState`, `includeAutomationWrites` | `fromState`, `toState`, `planId`, `planName`, `mrrMinor`, `previousMrrMinor`, `currency`, and `originProcedureId`, `originRunId` for a change a procedure made | `billing-state:<tenantId>:<revision replaced>` |
| `saas.plan-changed` | A workspace moves to another effective plan | `direction` (`upgrade`, `downgrade`), `includeAutomationWrites` | `fromPlanId`, `toPlanId`, `fromPlanName`, `toPlanName`, `direction`, `billingState`, and `originProcedureId`, `originRunId` for a change a procedure made | `plan:<tenantId>:<revision replaced>` |
| `saas.workspace-deletion-requested` | An owner deletes a workspace: access closes now, the data goes after the retention period | none | `requestedBy`, `planId`, `hadStripeSubscription`, `retentionDays`, `deletesAfter` | `workspace-deletion-requested:<operation id>` |
| `saas.free-access-ending` | Once, about three days before a workspace's complimentary access ends | none | `freeUntil`, `planId`, `daysLeft` | The id of the owners' warning notification |
| `saas.tenant-deleted` (deprecated) | A workspace's data is deleted at the end of retention | none | `operationId` | The deletion operation id |

### When a trigger fires again

1. The Stripe triggers fire once per Stripe event. A redelivery the webhook admission already processed fires nothing. Processed records are kept 90 days, so a redelivery after that fires again with the same `deliveryId`.
2. Stripe does not order its events. A late `pending` refund update can arrive after `succeeded`: compare `at`, which is when Stripe created the event.
3. `saas.billing-state-changed` and `saas.plan-changed` fire from the billing publication, which is fenced on the revision it replaces: one change fires once, whichever webhook, cron or operator action published it. The first publication of a workspace fires neither; a new workspace is `dms.tenant-created`. A plan migration publishes as soon as each workspace is migrated. A scheduled plan change fires `saas.plan-changed` when it lands, not when it is scheduled.
4. `saas.free-access-ending` is claimed in the `saas_automation_claims` table before it fires, so the daily job that sees one end date on up to four runs fires once. Moving the end date fires again with a new `deliveryId`. Claims older than 30 days are removed by the daily Stripe webhook event cleanup.
5. `saas.subscription-started` from provisioning fires again with the same `deliveryId` when a lost lifecycle receipt is replayed. A subscription a Checkout completed fires only from Checkout.
6. Every trigger hands its event over best-effort: the change that caused it never waits for, or fails with, the procedures it starts.

### Changes procedures make

A suspension or reactivation made by `saas.suspend-workspace` changes the billing state, and can land a plan change waiting on it. `saas.billing-state-changed` and `saas.plan-changed` ignore a change a procedure's write published unless the procedure arms them with `includeAutomationWrites`; the event then names the procedure and run in `originProcedureId` and `originRunId`. Past five such events of one trigger and workspace within a minute, the next ones are dropped and a warning is logged, so procedures that answer each other stop. The count is per instance.

Changes that other modules' procedures make (a DMS member action that changes seats, for example) reach the SaaS module without their origin, and count as ordinary changes.

## Actions

Every action takes the workspace as `tenantId` (no default workspace) and fails the step with `unknown workspace "<id>"` for an id that is not a workspace, except where stated. A refusal of the SaaS module fails the step with its message key.

| Action | Writes | What it does | Inputs | Outputs |
| --- | --- | --- | --- | --- |
| `saas.suspend-workspace` | yes | Suspends a workspace and pauses Stripe collection, or reactivates it when `suspended` is false. A workspace already in the requested state is left as it is (`changed: false`) | `tenantId`, `suspended` (default true) | `tenantId`, `suspended`, `subscriptionStatus`, `changed`, `operationId`, `effectiveAt` |
| `saas.notify-tenant-owners` | yes | Sends an in-app notification to the workspace owners | `tenantId`, `title` (1 to 200 characters), `description` (1 to 2000), `icon`, `linkTo`, `idempotencyKey` | `ok`, `recipientCount` |
| `saas.add-platform-note` | yes | Adds an internal note to a workspace or a user, shown to operators as written by **Automation** | `targetType` (`workspace`, `user`), `targetId`, `content` (1 to 4000 characters), `idempotencyKey` | `noteId`, `created` |
| `saas.get-workspace` | no | Reads the billing snapshot of the workspace directory. An unknown or deleted workspace answers `found: false` | `tenantId` | `found`, `name`, `billingState`, `planId`, `planName`, `planInterval`, `planBillingMode`, `pendingPlanId`, `isComplimentary`, `seats`, `members`, `mrrMinor`, `currency`, `renewalKind`, `renewsAt`, `stateSince`, `ownerStatus` |
| `saas.get-workspace-owner` | no | Reads the joined owner, or the invitee who will own the workspace | `tenantId` | `found`, `status`, `userId`, `name`, `email`, `language` |
| `saas.get-plan-constraints` | no | Reads the seat cap and seats used, the plan's features with inheritance applied, and any scheduled or blocked change | `tenantId` | `found`, `planId`, `planName`, `maxMembers`, `occupiedSeats`, `seatsAvailable`, `features`, `pendingPlanId`, `pendingPlanName`, `effectiveAt`, `blocked`, `admissionBlocked`, `incompatibilityCodes` |
| `saas.get-upcoming-invoice` | no | Reads the next invoice as Stripe prices it, from the preview cache when it is fresh. A Stripe failure answers `unavailable` | `tenantId` | `status`, `reason`, `currency`, `amountDueMinor`, `totalMinor`, `subtotalMinor`, `taxMinor`, `billingDate`, `periodStart`, `periodEnd`, `lineCount`, `computedAt` |
| `saas.list-workspaces` | no | Lists live workspaces of the directory a page at a time, by workspace id | `billingState`, `planId`, `isComplimentary`, `renewalKind`, `renewsBefore`, `limit` (1 to 200, default 50), `cursor` | `workspaces`, `tenantIds`, `count`, `nextCursor` |
| `saas.list-segment-users` | no | Lists the users of a segment's last evaluation a page at a time, by user id. It does not evaluate the segment again | `segmentId`, `limit` (1 to 200, default 50), `cursor` | `found`, `segmentName`, `evaluatedAt`, `total`, `users`, `userIds`, `count`, `nextCursor` |

`saas.list-workspaces` and `saas.list-segment-users` are platform-wide and take no workspace. Pass `nextCursor` back as `cursor` to read the next page; it is null on the last one.

### Retries and test runs

1. `saas.suspend-workspace` records the operation in the operator journal under an id made of the run, the step, the workspace and the requested action: a retried step answers the recorded result and calls Stripe once, and each workspace of a for-each loop gets its own operation.
2. `saas.notify-tenant-owners` and `saas.add-platform-note` deduplicate per step and `idempotencyKey` (wire a trigger's `deliveryId`), else per run, step and content. A notification's key also holds its workspace, and a note's id its target, so a for-each loop over several workspaces or targets with one key notifies each workspace's owners, an owner of several of them included, and writes one note on each. A notification that cannot be stored fails the step.
3. In a test run, the three write actions check their inputs and the workspace, write and send nothing, and answer what they would: the operation or note id, and the number of owners who would be notified.

### Who wrote it

A note or a suspension a procedure makes is attributed to `automation:<procedure id>`. Any platform operator can delete such a note.

## Data node

`saas.format-money` writes an amount in minor units as money text: `amountMinor`, `currency` (three letters, any case) and `locale` (default `en-GB`) give `text` and `amount` in major units. 6900 EUR in `fr-FR` gives `69 €`, 6950 gives `69,50 €`, 500 JPY gives `JP¥500`. The minor-unit exponent is ISO 4217's; Stripe bills a few currencies (HUF and TWD among them) with a different one. A currency that is not three letters or a malformed locale fails the step that reads it.

## What a run records

A run stores the outputs of every step it executed. These SaaS nodes put contact data in it, because delivering it is their purpose:

1. `saas.get-workspace-owner`: the owner's or invitee's name, e-mail and language.
2. `saas.list-segment-users`: the e-mail, name and language of up to 200 users per page.
3. `saas.notify-tenant-owners` and `saas.add-platform-note`: the text the procedure wrote.

`saas.get-workspace` and `saas.list-workspaces` leave the owner's name and e-mail out. No node records a Stripe secret, a payment method or raw webhook data.

## Workspace creation and deletion

1. Workspace created: use the DMS trigger `dms.tenant-created`. It fires for self-serve workspaces and for workspaces an operator creates, once both are provisioned. For a workspace an operator creates for an owner who has no account yet, it carries no owner user id: the owner is only invited. Read the SaaS side with `saas.get-workspace` and `saas.get-workspace-owner`. A provisioning that fails after the DMS handler ran fires `dms.tenant-created`, then `dms.tenant-deleted` for the same workspace.
2. Workspace deletion requested by an owner: `saas.workspace-deletion-requested`.
3. Workspace data deleted: use the DMS trigger `dms.tenant-deleted`, which carries the workspace name and owner.

## Deprecated nodes

`saas.tenant-deleted` is replaced by the DMS trigger `dms.tenant-deleted`. Saved procedures keep working, and arming one logs a warning naming it. Port mapping: `tenantId`, `at` and `deliveryId` are the same; `operationId` has no counterpart. It is removed in the first SaaS module release after the DMS release that ships `dms.tenant-deleted` has been out one minor version.
