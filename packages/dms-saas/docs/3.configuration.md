The module reads its options from its entry in `antelope.config.ts`. Only `stripe` is required.

## Options

| Option | Type | Default | Description |
| --- | --- | --- | --- |
| `stripe.secretKey` | `string` | required | Stripe secret key. A key that does not start with `sk_`, or that contains `placeholder` (such as `sk_test_placeholder`), is not usable, and the module then makes no Stripe call. |
| `stripe.publishableKey` | `string` | required | Stripe publishable key, sent to the browser for the card element. |
| `stripe.webhookSecret` | `string` | required | Signing secret of the webhook endpoint that targets `/api/saas/webhooks/stripe`. |
| `stripe.readTimeoutMs` | `number` | `4000` | How long, in milliseconds, a Stripe read that a page renders (billing status, next invoice preview, VAT check) waits before the page renders without it. Writes keep the timeout and retries of the Stripe SDK. |
| `stripe.readMaxNetworkRetries` | `number` | `0` | How many times such a read is retried after a network failure. |
| `admissionMode` | `"open"` or `"invitation-only"` | `"open"` | `invitation-only` closes public registration. Invitations keep working. Any other value stops the module at start. |
| `registration.paymentMethod` | `"required"`, `"optional"` or `"none"` | `"required"` | Whether public registration asks for a card. See [Registration](#registration). Any other value stops the module at start. |
| `publicScreens.register` | `boolean` | `true` | `false` frees the `register` slug for your own page. |
| `publicScreens.pricing` | `boolean` | `true` | `false` frees the `pricing` slug for your own page. |
| `allowedRedirectHosts` | `string[]` | host of the DMS `clientBaseUrl` | Hosts accepted as return URLs of Stripe Checkout and the billing portal, matched on `URL.host`. Only `http` and `https` URLs pass. A set value replaces the default, so list every host you need. In a development runtime, loopback hosts are accepted without an entry. |
| `defaultPlanSlug` | `string` | first free plan | The free plan every workspace falls back to. See [Default plan](#default-plan). |
| `upcomingInvoicePreviewCacheTtlSeconds` | `number` | `3600` | How long the upcoming invoice preview of a workspace is cached. `0` prices every request with Stripe. Plan, billing identity and invoice changes clear the cache sooner. A negative or non-finite value stops the module at start. |
| `reportingCurrency` | `string` | `"EUR"` | ISO 4217 code the back office reports recurring revenue in, read in upper case. Amounts in other currencies are shown apart and never converted. |
| `requiredPlanChangePolicy` | `string` | unset | Name of the inventory [plan change policy](/docs/modules/saas/reference/lifecycle-and-usage#plan-changes) that a deferred downgrade requires. While that policy is not registered, such changes fail closed. |
| `invoiceLineRequiredProviders` | `string[]` | `[]` | Invoice line provider IDs that every cycle invoice waits for, even when a provider has not registered yet as the invoice is created. |
| `invoiceLineRecoveryDiscoverySince` | `string` (ISO instant) | unset | The instant from which the module may discover and take over cycle renewal drafts of managed subscriptions whose `invoice.created` never registered a line injection task. Unset, or a value that is not a date, turns discovery off. |

The module publishes these values to the browser through its frontend module options, under `useDmsRuntimeConfig().public.dmsSaas`:

- `stripePublishableKey`, from `stripe.publishableKey`.
- `admissionMode`.
- `registrationPaymentMethod`, from `registration.paymentMethod`. The registration screens follow it only until the server tells them the policy it applies (see [Registration](#registration)).
- `publicScreens`, the IDs of the bundled public screens the deployment serves.

The Stripe secret key and the webhook secret never reach the browser.

The frontend registration of the module declares `/api/saas/register/finalize` in `authEstablishEndpoints`, so the frontend server lets its `POST /auth/establish` route open a session from that endpoint without any environment variable. See [Installation](/docs/modules/saas/installation).

## Registration

Public registration asks for an account (name, e-mail address, password) and the acceptance of the terms, plus a card when the deployment asks for one. The workspace it opens lands on the default plan, under a default name that its owner renames from the workspace settings. Customer type, billing address, VAT number and plan choice belong to the upgrade flow. While the catalogue has no default plan, registration answers `409 saas.errors.plan.no_free_plan`.

`POST /api/saas/register` checks the password against the DMS password policy (`isPasswordCompliant` from `@antelopejs/interface-dms/auth/password`) before it looks up the e-mail address or creates anything. A password that fails the policy gets `400 saas.errors.registration.password_policy`. The OAuth completion carries no password.

Two module options shape registration:

```json
{
  "modules": {
    "dms-saas": {
      "config": {
        "admissionMode": "open",
        "registration": { "paymentMethod": "required" }
      }
    }
  }
}
```

`registration.paymentMethod` decides whether registration asks for a card.

| Value | Behaviour |
| --- | --- |
| `required` (default) | The card step is shown and must be completed. The workspace gets a Stripe customer that holds the card, and a free subscription. While the free plan has no Stripe price, that subscription is local, and the upgrade checkout replaces it on the same customer. The free-workspace-per-card cap applies when it is on. |
| `optional` | The card step is shown, and the visitor may add a card later. Without a card, the workspace is card-less, as under `none`. |
| `none` | The card step is never shown. `GET /api/saas/register/setup-intent` answers `400 saas.errors.registration.payment_method_disabled`, and Stripe is never called. The workspace gets a local free subscription with no Stripe customer, and the upgrade checkout creates the customer when the owner first pays. A card sent anyway is ignored. |

### Without a usable Stripe key

Without a usable Stripe secret key, no card can be confirmed. The server then applies `none` whatever the option says. Registration lands on the free plan without a card or any Stripe call, and `GET /api/saas/register/setup-intent` answers `400 saas.errors.registration.payment_method_disabled`. A free workspace created in the app asks for no card either.

`GET /api/saas/register/plan` answers the policy the server applies in `paymentMethod`. The frontend server cannot tell whether the backend holds a usable key, so `registrationPaymentMethod` stays the configured value, and the registration screens follow it only until that answer arrives. The page renders on the server with the configured card step. Once the answer arrives, a screen without a usable key drops that step, and it never asks for a SetupIntent, because it mounts the card field only after the answer.

### When Stripe cannot be used

Stripe can be configured and still unusable: it refuses the key, the key lacks a permission, Stripe is unreachable, or it answers with a 5xx status or a rate limit. The registration, workspace creation, SetupIntent and plan preview routes then answer `503 saas.errors.stripe.unavailable` instead of an unhandled 500, and the screens show the translated message. Without a usable key, the SetupIntent route of workspace creation answers `503 saas.errors.stripe.not_configured`. Under `optional`, the visitor can still add the card later.

The operator routes that need Stripe follow the same rule. The credit note preview and issue, the manual upgrade and its preview, and the balance credit answer `503 saas.errors.stripe.not_configured` without a usable key, before any Stripe call or journal entry. They answer `503 saas.errors.stripe.unavailable` when Stripe cannot be used. Granting complimentary access answers `503 saas.errors.stripe.unavailable` when Stripe cannot cancel the paid subscription. Without a usable key, the available credit of a workspace shows nothing.

### Free workspaces per card

The free-workspace-per-card cap is the **Free workspaces per card** billing rule of the back office. Its default is `0`, which turns it off. When an operator turns it on, and Stripe has a usable key, every free workspace created in the app asks for a card. Once a card backs that many free workspaces, another workspace with the same card asks for a paid plan.

Under `optional` and `none`, a card-less workspace has no card fingerprint, so the cap does not apply to it. The only remaining limit on free workspaces is one account per e-mail address.

### Which entry points the options cover

`registration.paymentMethod` covers both public entry points, `POST /api/saas/register` and the `auth/no-workspace` completion, and nothing else. Invitation sign-up never asks for a plan or a card, whatever `admissionMode` and `registration.paymentMethod` say. Workspace creation inside the app ignores `registration.paymentMethod`. There, a paid plan asks for a card, and a free plan asks for one only under the free-workspace-per-card cap.

`admissionMode: "invitation-only"` closes public registration. Every `/api/saas/register` route answers `403 saas.errors.registration_closed` before it reads the card policy. Workspace creation inside the app answers the same error to every user except a platform owner. The registration screens show a "Registration is closed" state instead of the form, and the login page drops its sign-up link. Invitations keep working.

`useSaasRegistration()` reads `admissionMode` and `registrationPaymentMethod` from `useDmsRuntimeConfig().public.dmsSaas`.

### The SetupIntent behind the card step

The server restricts the Stripe SetupIntent behind the card step to cards, through `allowed_payment_method_types: ["card"]`, because Stripe is retiring `payment_method_types` on SetupIntent creation. The Payment Element is created from the client secret alone, because Stripe refuses `paymentMethodTypes` next to a `clientSecret`.

### Registration rate limit

`POST /api/saas/register` accepts 20 calls per client address in a 60-second window, refused ones included. The 21st answers `429 Too many requests` with a `Retry-After` header, and the module creates nothing for it. The limit is not configurable.

The `@RateLimit` decorator of `@antelopejs/interface-api-util` counts in the memory of each backend process, by the socket address of the request. Each replica keeps its own count, so a client spread across N replicas can register up to N × 20 times per window, and a restart resets the count. Behind a reverse proxy, the socket address is the proxy's, so all the visitors that reach one replica through that proxy share its 20 calls.

## Default plan

A workspace is never without a plan once the catalogue has a default plan. The default plan is the active, non-deleted plan with a price of 0 or less, open to individuals (audience `any` or `individual`), with the lowest `order`. `defaultPlanSlug` picks another plan among those candidates:

```json
{ "modules": { "dms-saas": { "config": { "defaultPlanSlug": "free" } } } }
```

A `defaultPlanSlug` that names no candidate is ignored with a warning, and the lowest-ordered candidate applies.

Registration opens the default plan. The module attaches it, as an active card-less subscription, when a workspace is created by registration, and when the DMS provisions the `default` tenant of the platform. When a platform owner publishes the first free plan, or a catalogue edit makes another plan the default, the module attaches the new default once to every workspace that has no subscription at all. Nothing replays this at startup or on a cron. The billing page still covers a plan-less workspace on its first read. A workspace that holds any subscription is never touched. While the catalogue has no free plan, nothing is attached and the module logs a warning.

A catalogue written straight into the plan table, by a seed or an import, does not go through the routes of the platform owner. Attach the plan to the workspaces it should cover in the same seed.

Once attached, the permissions of the plan cap the members of the workspace like any other plan. See [Tenant owner permissions](/docs/modules/saas/extending#tenant-owner-permissions).
